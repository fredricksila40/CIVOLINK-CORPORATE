Developers and integration

How CIVOLINK is meant to be built

Technical direction for the umbrella platform and its products: independent systems, explicit boundaries, and an integration story that never claims more than it has proven.

Direction document No public API today
Illustrative content throughout. No CIVOLINK public API is published by this page. Every payload, endpoint path and field name below is a documentation example chosen to explain a pattern — it is not a specification, and it must not be implemented against. No API keys, credentials, private endpoints or internal hostnames appear anywhere in this suite.

Developer introduction

Build against a product, not a monolith

Each CIVOLINK product is an independent application with its own backend, database, security controls and deployment lifecycle. There is no central platform API that everything hangs from — by design.

That choice has a practical consequence for integrators: you integrate with the product that owns the data you need, under that product's own contract, rate limits and review process. The umbrella website's job is to tell you which product that is.

Product architecture overview

Independent applications, shared presentation

The layering below is an architectural intent. It is not a description of deployed infrastructure, and no deployment has been verified as part of this suite.

Presentation layer

The umbrella website: brand, navigation, corporate content and product discovery. Static content, no product data, no privileged operations.

Product applications

CIVOLINK WIFI and Biashara Flow: each with its own server code, data store, authentication model, configuration and release process.

Boundary controls

Security and operational boundaries per product: secrets stay with the system that needs them, and corporate content management never reaches administration.

Independence is the point. Failure of the corporate website must not interrupt a customer-facing product, and a product incident must not take down corporate communication. This is a design requirement, not a measured property of anything deployed today.

API and integration philosophy

Small, explicit, versioned — when they exist

How we intend to expose capability

  • Per-product contracts. An integration belongs to one product's API, never to a vague "platform" endpoint.
  • Version from day one. Breaking changes ship as new versions; existing versions get a documented sunset.
  • Explicit responses. Success and failure are machine-readable states, not HTTP status codes used creatively.
  • Idempotent writes. Repeating a request must not create duplicate business effects.
  • Documented, not implied. Nothing is supported unless it is written down in the product's documentation.

How we intend to authenticate

  • Scoped credentials. Least privilege per integration, revocable without touching the rest of the system.
  • Server-side secrets. Credentials live in server configuration, never in browser code or a repository.
  • Signed callbacks. Inbound webhooks are verified by signature and timestamp before any state change.
  • No shared session assumption. Products do not assume a central login exists — none does today.
  • Review before production. New integrations are reviewed rather than self-served into production.

Security principles

Boundaries before features

These are the principles the reference suite is written to respect. They are commitments about how future systems should be built, not attestations about systems already in production.

Fail closed

If a check cannot be completed — signature, configuration, permission — the safe outcome is refusal, not a best-effort guess.

Secrets stay server-side

No keys, tokens or credentials in HTML, JavaScript, client storage, screenshots or documentation examples.

Least privilege

Corporate content access never implies administrative access to customer records, payments or network equipment.

Verify, don't trust

Inbound events are authenticated and validated server-side; client-supplied claims are treated as claims.

Auditability

State-changing operations should be attributable and replay-safe, with unresolved records preserved rather than discarded.

Separation of duties

Website content publication and application administration are distinct roles held by distinct systems.

Data minimisation

Collect only what a product needs, keep it only as long as its purpose requires, and define retention deliberately.

Evidence over assertion

A control is only claimed once it has been demonstrated under controlled conditions and the evidence is recorded.

Integration example

A pattern, not a specification

The example opposite shows the shape of a future product-level integration: explicit states, an idempotency key and a signature scheme. Field names and values are invented for clarity.

  • No real endpoint, host, credential or signature algorithm is published here.
  • The payload must not be implemented against — it will change when the owning product defines its actual contract.
  • Any real integration would be documented under the product's own documentation portal when that exists.
Never publish working credentials in examples. If a real contract is ever written here, it will use placeholder tokens that are structurally invalid on purpose.
